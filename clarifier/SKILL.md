# clarifier

## 协作约定

- 本 skill 与同级的 `todos`、`implement` 一同分发。`todos` 负责任务 Markdown 的状态目录约定；`implement` 在任务可执行后负责落地、验证与审查摘要。
- 当用户使用“开始澄清”或显式调用本 skill 时，按以下流程处理。其他情况不自动进入完整澄清流程。

## 澄清与授权

- 先尽可能地收集相关“上下文”作为下一步的决策依据，“上下文”包括：1.目前用户已经明确提供的文件、文字、链接等；2.基本现状事实，在授权范围内读取文件、运行命令或检查环境；3.多方意见，尽可能使用目前已有的调研工具（如网络搜索等）收集相关的最佳实践例子、基本共识、真实痛点等与当前情景相关的信息。
- 通过与用户进行多轮讨论明确一下内容板块的细节，内容板块包括：背景与动机、最终目标、基本假设、实施边界以及实施细节、可接受的风险、验收标准。
- 当讨论的信息不足以创建以上内容板块时，需持续讨论、澄清，不猜测，直至确保无歧义为止。
- 当讨论的信息已经足够，先加载 [todos](../todos/SKILL.md)，理解其规则和约定，再向用户简述本次任务的每个内容板块的内容以及将要如何新建或修改 Markdown 代办文档，最后征求用户是否新建或修改 Markdown 代办文档。
- 只有用户明确肯定时，才可新建或修改任务 Markdown；否则继续回到讨论环节，直到用户同意才可新建或修改。

## 任务 Markdown 格式要求

严格按照如下格式来书写 Markdown 代办文档，保留所有二级章节板块内容，不添加其他层级标题，每个章节正文不做篇幅要求，但需要保持简洁和无歧义，以降低审核压力。

```markdown
# <任务标题>

## 背景与动机
<基本前提、前情提要，以及能简要证明问题真实存在的事实或证据等。>

## 最终目标
<可理解、无歧义、可量化的目标>

## 基本假设
<科学前提、假设>

## 实施边界以及实施细节

<TL;DR：解决思路与方案重点>
<已拍定的路径、技术做法、重点细节、最终取舍。>

## 可接受的风险
<从务实、科学角度说明当前方案可能失效、退化或需要谨慎的地方。>

## 验收标准
<可无歧义按照步骤进行验证的操作>

## 更多细节
<相关依赖、相关文件和父子任务关系。>
<其他有必要补充的细节>
```
